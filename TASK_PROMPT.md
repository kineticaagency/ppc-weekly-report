# Общий промпт: еженедельный мониторинг рекламных проектов

Развивай внутренний инструмент агентства для еженедельного мониторинга
контекстной рекламы. Основной пользовательский интерфейс — одна Google Таблица,
где каждому проекту соответствует отдельная вкладка с названием домена.

Главный сценарий: каждый понедельник открыть одну таблицу, быстро увидеть
состояние проектов, понять, что изменилось, почему, выполняется ли план и где
нужно вручную зайти в рекламный кабинет для дополнительной диагностики.

## Общие принципы

1. Источники и правила задаются отдельно для каждого проекта. Не унифицируй
   исходные системы искусственно; унифицируй итоговый управленческий ответ.
2. Работай с Яндекс.Директом, Метрикой, Roistat и другими внешними системами
   только на чтение. Не изменяй кампании, ставки, объявления, цели, заявки или
   статусы.
3. Не придумывай доступы, идентификаторы, цели, статусы, классификацию лидов,
   атрибуцию или плановые показатели. Если настройка не подтверждена, явно
   запроси её или покажи отсутствие данных.
4. Токены хранятся только в `.env.local`, а ключ сервисного аккаунта Google — в
   `.secrets/google-service-account.json`. Не выводи секреты, не записывай их в
   конфигурацию и не коммить в Git.
5. Минимизируй API-запросы: запрашивай только необходимые поля, агрегируй данные
   пакетно, не перезапрашивай сохранённую историю без необходимости.
6. Все вычисления выполняй обычным кодом: агрегацию, CPC, CTR, CR, CPA,
   сравнение недель, план/факт, пороги отклонений, вклад источников и кампаний,
   зрелость лидов и выбор значимых фактов.
7. LLM используй только для одного короткого естественного комментария по уже
   рассчитанному набору фактов. Не передавай сырые таблицы. Если значимых фактов
   нет, не вызывай LLM.

## Структура проектной вкладки

- название проекта;
- дата и время последнего обновления по Москве;
- накопительная история: новые периоды добавляются вниз, прошлые не затираются;
- календарные месяцы с недельными строками и строкой «Факт»;
- краткий комментарий по последней завершённой неделе;
- блок план/факт текущего месяца на дату;
- единое спокойное оформление: Montserrat, вертикальное выравнивание по центру,
  показатели слева, числовые значения и заголовки по центру;
- рубли — целые, обращения — целые, CR — до десятых процента, отклонения — целые
  проценты;
- не показывать блоки Поиск/РСЯ ни на одной проектной вкладке. Эти срезы можно
  использовать внутри диагностики, но не выводить в таблицу.

Если завершённая неделя пересекает границу месяцев, визуально разделяй её между
месяцами, чтобы месячный факт совпадал с календарём. Для аналитического
сравнения используй полные недели понедельник–воскресенье.

## Аналитика

Сравнивай последнюю завершённую неделю с предыдущей. Основными факторами
изменения CPA считай CPC и CR, но учитывай расход, клики и абсолютное изменение
объёма конверсий. Приоритет диагностики: абсолютный вклад, относительное
изменение, затем размер выборки.

Порог динамики:

- менее 10% — нормальная динамика;
- 10–15% — зона внимания;
- более 15% — дополнительная диагностика.

Не ищи сложные причины при небольшом изменении. Отличай подтверждённые данными
причины от гипотез внутри аналитического слоя, но не используй технические
ярлыки в пользовательском комментарии.

Комментарий обычно содержит 3–5 предложений: результат по CPA и обращениям,
главную причину через CR/CPC, при необходимости вторичный фактор, качество лидов
и предупреждение о незрелости данных. Пиши естественно, как PPC-специалист, без
перечисления всех метрик и повторов.

## План/факт и подсветка

План на дату рассчитывай пропорционально прошедшим календарным дням с учётом
реального числа дней в месяце. Отклонение:

`(Факт - План на дату) / План на дату × 100%`.

Направление KPI настраивается для каждого проекта:

- `higher_is_better` — обращения и CR;
- `lower_is_better` — CPA;
- `deviation_is_bad` — расход;
- `ignore` — клики и CPC, если проектом не задано иначе.

До 10% не подсвечивай. Негативные 10–20% выделяй жёлтым, более 20% — красным.
Значимые положительные отклонения более 10% выделяй зелёным. Расход выше или
ниже плана требует внимания; интерпретируй его совместно с выполнением плана по
обращениям и CPA. Цветовая подсветка применяется только в блоке план/факт.

## Текущие проекты

- `reduktor40.ru`: Яндекс.Директ — рекламные показатели; Roistat — заявки и
  качество; Google Sheets — план. Классификацию статусов бери только из
  `config/reduktor40.json`. При большой доле необработанных заявок показатели
  качества показывай как предварительные без категоричного вывода.
- `asko-hall.ru`: весь аккаунт `asko-hall-direct`; Метрика, счётчик `69158290`,
  целевые визиты целей покупки и отправки заявки с атрибуцией
  `cross_device_last_significant`, только трафик Яндекс.Директа; Roistat-проект
  `187383`, уникальные звонки с маркером `direct1`. Обращения — сумма этих
  целевых визитов и уникальных звонков. Не показывай составляющие отдельно.
- `loglab.ru`: весь аккаунт `porg-zsyy7hra`; Метрика, счётчик `78913450`,
  уникальные целевые визиты подтверждённых целей из трафика Яндекс.Директа;
  Roistat не используется.

Актуальные ID целей, ссылки на планы, KPI-направления и настройки источников
всегда бери из `config/*.json`, а не из текста этого промпта, если они различаются.

## Порядок безопасной работы

Перед изменениями изучи существующий код, конфигурацию проекта и состояние Git.
Сохраняй уже работающую логику других проектов. После изменений запускай тесты,
публикуй только целевую вкладку и контрольным чтением проверяй ключевые периоды,
план/факт, форматирование и отсутствие блоков Поиск/РСЯ. Сообщай о фактических
ограничениях API и не подменяй недоступные данные нулями.
